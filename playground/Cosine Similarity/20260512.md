## 📚 학습 정리

### 1. SQL self-join 디버깅 — 세 가지 버그

처음 짠 쿼리에서 결과가 이상하게 나왔고, 다음 세 가지가 원인:

#### (a) 연산자 우선순위 — 분자 전체 괄호 빠짐

```sql
-- 잘못된 코드
(t1.gas*t2.gas) + (t1.diesel*t2.diesel) + (t1.premium*t2.premium)
/ (t1.norm * t2.norm)
```

SQL 에서 `/` 가 `+` 보다 우선순위 높음. 실제 평가:

```
(a*x) + (b*y) + ((c*z) / norm_곱)
  ↑     ↑          ↑
 그대로 그대로  이것만 나뉨
```

→ 분자 전체 괄호 필수. **"식의 결과 범위 (cosine 은 -1~1)" 라는 사전 감각이 있었기에 이상함을 잡을 수 있었음.** 이 사전 감각이 디버깅의 절반.

#### (b) `norm` 이라는 변수명이 거짓말

`(gasoline^2) + (diesel^2) + (premium^2) as norm_2` — sqrt 가 빠져있어서 이건 실제로 ‖A‖² (제곱 노름). 진짜 노름이 아님.

→ sqrt 씌워서 진짜 노름으로. 그리고 변수명을 정직하게.

**메타 교훈**: 변수명이 거짓말하면 디버깅 비용 두 배. 일주일 후의 본인을 속이지 말기.

#### (c) null 처리 부족

`gasoline is not null` 만 걸려있고 diesel/premium 은 빠져있어서 분자에 null 끼면 전체가 null.

→ `coalesce(..., 0)` 으로 안전장치. 또는 셋 다 not null 로 거르기.

### 2. 코사인 결과 범위 사전 감각 — 디버깅 자산

`-1 ≤ cos ≤ 1` 이라는 범위를 미리 머리에 깔아두니 결과 이상함을 즉시 포착. 다른 metric 도 같은 식으로 미리 깔아두면 됨:

| Metric | 결과 범위 |
|---|---|
| Cosine similarity | -1 ~ 1 |
| Pearson correlation | -1 ~ 1 |
| Jaccard similarity | 0 ~ 1 |
| Chi-square statistic | 0 ~ ∞ |
| Euclidean distance | 0 ~ ∞ |

→ "이 식의 결과 범위가 어디여야 한다" 는 사전 지식이 디버깅의 첫 번째 도구.

### 3. N² × D 비용 분해 — N 과 D 의 비대칭성

오늘 던진 질문: *"컬럼이 6개 / 10개로 늘면 비용은?"*

```
한 쌍당 cosine 계산: 약 5D 회 산술 (O(D))
전체 비용: N² × D
```

| | 영향력 |
|---|---|
| **N (행 / 샘플 수)** | N² — **폭발적** |
| **D (열 / 차원 수)** | D¹ — 선형 |

N 두 배 → 비용 **네 배**. D 두 배 → 비용 **두 배**. 이 비대칭이 ML 시스템 설계의 핵심.

| | 무서운 분기점 | 도구 갈아탈 곳 |
|---|---|---|
| **N** | 10만 ↑ | brute force → ANN/LSH/FAISS |
| **D** | 1000 ↑ | self-join SQL → list/array 함수, 차원 축소 |

본인 현재 (N=1만, D=3) 는 **두 축 모두 가장 안전한 영역**. 그래서 brute force 가 통한 거. 운이 아니라 데이터 크기와 도구가 맞물려 있는 영역.

### 4. **차원 독립적 표현** — list 함수의 진짜 가치

```sql
-- self-join: 컬럼 D개 마다 D번 손코딩
(t1.gas*t2.gas) + (t1.diesel*t2.diesel) + (t1.premium*t2.premium)

-- list 함수: D 와 무관하게 동일
list_cosine_similarity(t1.vec, t2.vec)
```

→ 새 컬럼 (위도, 경도 같은 거) 추가하면 self-join 은 SQL 새로 짜야 함. list 버전은 **base CTE 한 줄만 바꾸면 끝**.

→ 임베딩 시대 SQL 의 표준 패턴. `pgvector` 의 `<=>` 도 같은 철학. **벡터 컬럼 하나로 차원 추상화.**

D=768 (BERT 임베딩) 이면 self-join 은 시작도 못 함. list 함수 한 줄로 끝.

### 5. DuckDB Lazy Evaluation — 0.2초의 비밀

처음에 `.df()` 빼고 짰을 때 12초가 아닌 **0.2초**에 끝남. 이상함.

```python
con.sql("...")        # ← 실제 안 돔. 실행 계획만.
display(relation)     # ← 이때 처음 몇 row 만 materialize
```

→ DuckDB Python API 는 **lazy**. `con.sql()` 은 `DuckDBPyRelation` 반환 (실행 계획 객체). 실제 실행은 `.df()`, `.fetchall()`, `.show()` 같은 action 호출 시.

본인이 자기도 모르게 전체 계산 회피했던 것. `.df()` 붙이고 다시 돌리니 12초로 정착.

이 패턴은 SQL 본진 사람한테 친숙한 개념의 변주:

| 단계 | SQL DB | Spark | DuckDB Python |
|---|---|---|---|
| 계획만 (lazy) | EXPLAIN | transformation | `con.sql(...)` |
| 실제 실행 (eager) | 쿼리 제출 | action | `.df()`, `.fetchall()` |

→ pandas (eager) 의 멘탈 모델로 DuckDB Python API 를 보면 헷갈림. DuckDB 는 본인 SQL 본진의 lazy 세계와 같은 결.

### 6. 빌트인 함수의 압도적 속도 — SIMD 의 위력

| | self-join (3단계) | list 함수 (4단계) |
|---|---|---|
| 결과 row | 1억 60만 | 5,302만 (대칭성 적용) |
| 시간 | 2분 8초 | **12초** |
| row 당 비용 | 1.28 μs | **0.24 μs** |

데이터양 절반 영향 빼고도 **약 5배 빠름**. 같은 산수, 같은 엔진인데 왜?

#### 추정 원인 세 가지

1. **SIMD 벡터화** — `list_cosine_similarity` 는 C++ 빌트인. CPU 한 명령으로 4~8개 float 동시 처리.
2. **컬럼 접근 비용 절약** — self-join 은 3개 컬럼 fetch, list 버전은 vector 컬럼 하나 fetch. 컬럼나르 스토리지에서 누적 차이 큼.
3. **식 평가 오버헤드 회피** — SQL 식 평가 트리 vs 단일 함수 호출.

#### 핵심 메타 — "표현이 짧을수록 빠를 가능성이 큼"

직관과 반대로 들리는 원칙:

| 영역 | 직접 짜기 (느림) | 빌트인 함수 (빠름) |
|---|---|---|
| numpy | `for i: sum += a[i]*b[i]` | `np.dot(a, b)` |
| pandas | row loop | `df.groupby().agg()` |
| SQL | self-join + 산수 | `list_cosine_similarity()` |

→ **잘 만들어진 빌트인은 표현도 짧고 + 실행도 빠름. 두 마리 토끼.** 어제 sklearn NearestNeighbors 가 N×K 로 직행해서 빠른 것과 같은 원리.

→ 데이터 분석가의 핵심 본능: **"이 작업에 빌트인 함수가 있나?"** 를 항상 한 번 더 묻기.

### 7. Spark / Databricks 환경의 같은 쿼리

| 엔진 | cosine 관련 빌트인 | 대안 |
|---|---|---|
| DuckDB | `list_cosine_similarity` | — |
| Databricks (Runtime 14+) | `cosine_similarity` (빌트인 추가됨) | Vector Search |
| OSS Spark SQL | **없음** | array + `aggregate` 고차함수로 손코딩 |
| PostgreSQL | `<=>` (pgvector 익스텐션) | UDF |
| BigQuery | `ML.DISTANCE`, `COSINE_DISTANCE` | — |
| Snowflake | `VECTOR_COSINE_SIMILARITY` | Cortex |

→ **벡터 연산은 RAG/LLM 시대 들어 모든 메이저 DBMS 의 표준 기능이 되어가는 중.** 다만 OSS Spark 만 아직 array 함수 + 고차함수 패턴이 메인.

#### OSS Spark SQL 패턴 (참고)

```sql
-- array + aggregate 로 손코딩
aggregate(
  zip_with(t1.vec, t2.vec, (a, b) -> a * b),
  cast(0 as double),
  (acc, x) -> acc + x
) / (sqrt(...) * sqrt(...))
```

→ 차원 독립적이긴 하나 표현이 깔끔하진 않음. DuckDB 한 줄과 비교.

#### 외울 가치 판단 (LLM 시대 메타)

- **함수 이름 자체는 외울 필요 없음** — 검색 1초
- **머리에 박을 것**:
  - "벡터 연산은 메이저 DBMS 다 있다" 는 패턴 인식
  - 옆 가족 함수들 (inner_product, L2 distance, manhattan)
  - 검색 키워드 (`<엔진명> cosine similarity function`)
  - 개념 (내적 / 노름곱)

함수는 사전, 개념은 머리. 사전은 그때그때 찾으면 됨.

### 8. DBeaver 가 뻗은 이유 — Embedded DB 의 호스트 의존성

DBeaver 에서 같은 list_cosine_similarity 쿼리 → 뻗음. 본인 가설: *"파이썬은 내 CPU, DBeaver 는 NAS CPU 써서 그런 거 아닌가?"*

→ **가설 방향은 좋은 질문이나 답은 빗나감.** 핵심 교정:

#### DuckDB 는 **Embedded DB** — "서버" 가 없음

```
Python 환경:
[본인 노트북]
  └─ Python 프로세스
      └─ DuckDB 엔진 (Python 프로세스 안에 임베드)
          └─ NAS (MinIO) 에서 parquet 파일 stream 으로 읽기

DBeaver 환경:
[본인 노트북]
  └─ DBeaver (JVM 프로세스)
      └─ DuckDB 엔진 (JVM 프로세스 안에 임베드)
          └─ NAS (MinIO) 에서 parquet 파일 stream 으로 읽기
```

둘 다 **본인 노트북 CPU/RAM** 으로 돔. NAS 는 단순 파일 서버 역할만.

#### 클라이언트-서버 DB vs Embedded DB

| | 클라이언트-서버 (PostgreSQL, BigQuery, Spark) | Embedded (DuckDB, SQLite) |
|---|---|---|
| 연산 위치 | 서버 머신 | **클라이언트 프로세스** |
| 본인 가설 적용 | 맞음 — 서버 부족하면 죽음 | **빗나감** — 본인 노트북에서 다 돔 |
| 결과 전송 | 서버 → 클라이언트 결과만 | 클라이언트가 데이터 끌어와서 처리 |

본인이 핀다에서 매일 쓰는 BigQuery 는 클라이언트-서버. 그래서 "쿼리 날리면 서버에서 돈다" 멘탈 모델이 깔려있었음. 그 모델이 DuckDB 에선 안 맞음.

#### 진짜 원인 — 호스트 프로세스 차이

| | Python | DBeaver (JVM) |
|---|---|---|
| fetch 방식 | `.df()` 가 컬럼나르로 한 방에 묶음 | GUI grid 용 row 단위 fetch (5천만 Java object 생성) |
| 메모리 한계 | 시스템 RAM 전체 | **JVM 힙 1~2GB** (기본값) |
| 결과 | 12초에 끝남 | 6,400,000 rows fetched - 20s 진행 중에 뻗음 |

→ **DuckDB 엔진 자체는 동일.** 문제는 DBeaver(JVM) 가 결과를 받아 GUI 에 그릴 때 죽은 거.

#### 메타 — "연산이 어디서 일어나는가" 는 평생 질문

데이터 시스템 다루는 사람의 핵심 본능:

- BigQuery → Google 클라우드 서버
- Spark cluster → cluster 노드들
- pandas → 본인 머신, 메모리 안
- **DuckDB → 본인 머신, 호스트 프로세스 안**
- SQLite → 본인 머신, 호스트 프로세스 안

→ "내 코드의 무거운 일이 어디서 도는가" 를 항상 의식하는 게 분석 시스템 설계의 1번 항목. **이 질문 던지는 본능은 이미 있음.** 다만 DuckDB 가 embedded 라는 사실을 박으면 그림 완성.

#### 실무 패턴 — GUI 에 큰 결과 띄우지 말기

```sql
-- 패턴 1: 집계까지 SQL 안에서
select uni_cd_a, count(*), avg(cosine_similarity)
from (...) group by uni_cd_a

-- 패턴 2: 파일로 저장
copy (...) to '/path/output.parquet'
```

GUI tool 은 확인용 (LIMIT 100) 으로만. 큰 결과는 SQL 안에서 집계해서 줄이거나 파일로 떨구는 게 일반 패턴. BigQuery 콘솔에서 `select *` 안 하고 항상 `limit` 붙이는 본능과 같음.

## 🎁 오늘 최종 코드

### 5단계 — 순수 SQL self-join (확장성 검증용)

```sql
with base as (
  select 
    uni_cd,
    sqrt(
      pow(coalesce(gasoline, 0), 2)
      + pow(coalesce(diesel, 0), 2)
      + pow(coalesce(premium_gasoline, 0), 2)
    ) as norm,
    coalesce(gasoline, 0) as gasoline,
    coalesce(diesel, 0) as diesel,
    coalesce(premium_gasoline, 0) as premium_gasoline
  from read_parquet('s3://petroleum-project/station_price/agg/*/*.parquet')
  where gasoline is not null and part_dt = '20260425'
)
select 
  t1.uni_cd as uni_cd_a,
  t2.uni_cd as uni_cd_b,
  ((t1.gasoline*t2.gasoline) + (t1.diesel*t2.diesel) + (t1.premium_gasoline*t2.premium_gasoline))
    / (t1.norm * t2.norm) as cosine_similarity
from base t1 cross join base t2
where t1.uni_cd < t2.uni_cd   -- 대칭성으로 절반
```

5천만 row 결과, 본인 환경에서 2분 8초 (대칭성 미적용 1억 row 기준).

### 4단계 — DuckDB list_cosine_similarity (실전용)

```sql
with base as (
  select 
    uni_cd,
    [coalesce(gasoline, 0), coalesce(diesel, 0), coalesce(premium_gasoline, 0)] as price_vector
  from read_parquet('s3://petroleum-project/station_price/agg/*/*.parquet')
  where gasoline is not null and part_dt = '20260425'
)
select 
  t1.uni_cd as uni_cd_a,
  t2.uni_cd as uni_cd_b,
  list_cosine_similarity(t1.price_vector, t2.price_vector) as cosine_similarity
from base t1 cross join base t2
where t1.uni_cd < t2.uni_cd
```

5천만 row 결과, **12초**. 5배 빠르고 차원 독립적.

## 💡 오늘의 큰 깨달음

1. **변수명이 거짓말하면 디버깅 비용 두 배**: `norm_2` 가 실제로는 ‖A‖² 였던 사례. 일주일 후의 본인을 속이지 말기.

2. **결과 범위 사전 감각이 디버깅의 첫 도구**: cosine 은 -1~1, Pearson 은 -1~1, Jaccard 는 0~1 — 미리 깔아두면 이상한 결과 즉시 포착.

3. **N 과 D 의 비대칭성**: N 은 N² 로 폭발, D 는 선형. 본인은 두 축 모두 안전 영역에 있어서 brute force 가 통한 것.

4. **차원 독립적 표현 = 임베딩 시대의 표준**: list/array 컬럼 + 빌트인 함수 패턴. D 가 768 이든 3 이든 SQL 동일.

5. **잘 만들어진 빌트인은 두 마리 토끼**: 표현 짧음 + 실행 빠름. SIMD/벡터화 같은 저수준 최적화를 라이브러리가 다 해놓음. **"이 작업에 빌트인 함수가 있나?" 를 항상 한 번 더 묻기.**

6. **DuckDB Python API 는 lazy**: `con.sql()` 만으론 실행 안 됨. `.df()` 같은 action 호출 시 실행. 본인 SQL 본진의 lazy 세계 (EXPLAIN, Spark transformation) 와 같은 결.

7. **함수명은 사전, 개념은 머리**: 함수 이름 외울 필요 없음 (검색 1초). 박을 건 "이 카테고리의 함수가 어딘가에 있다" 는 패턴 인식 + 개념 자체.

8. **DuckDB 는 Embedded DB — 서버가 없음**: 본인이 BigQuery 멘탈 모델 ("서버에서 돈다") 을 무의식적으로 적용하고 있었음. SQLite/DuckDB 류는 클라이언트 프로세스 안에서 돔. DBeaver 가 뻗은 건 NAS 탓이 아니라 JVM 힙 한계.

9. **"연산이 어디서 일어나는가" 는 데이터 시스템 평생 질문**: 분석 시스템 설계의 1번 항목. 본인은 이 질문을 던지는 본능이 이미 있음.
